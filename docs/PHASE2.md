# Phase 2: Xpert pipeline and screening

Status: built and tested. Not deployed. Two migrations are waiting to be shown and run.

## What was built

**One state machine for Xpert status.** `packages/shared/src/xpertStatus.ts` holds every allowed move, who may make it, what must be true first, and when a reason is required. The API, the buttons on screen and the tests all read that one table. Anything not listed is refused, and a test tries every illegal pair to prove it. The database repeats the allowed status values as a check, and one database function applies a change atomically: it refuses if the status moved since the screen loaded, updates the Xpert and writes the history row together.

**Rules the brief set, as built.**
- Applied moves to Guarantor Pending on its own once a guarantor is named.
- Guarantor Confirmed needs both the explainer message marked sent and a recorded yes on the callback. A no or a hesitation closes the application. No confirmation within the deadline (two weeks) closes it automatically.
- Skill Verification starts on its own once the guarantor is confirmed. A nudge shows in Approvals after two weeks. It never changes a status.
- Provisional Active needs a decision maker to approve, a confirmed guarantor and at least one passed piece of evidence with none waiting. The approver records who verified: BeyondX directly or a coordinator. That source shows wherever verification appears.
- Fully Active follows on its own from a confirmed reference (with no family or guarantor warning), a verified certification, or enough clean jobs.
- Under Review, Suspended and Removed need a reason, and only a decision maker can decide them. A guarantor retracting sends an active Xpert to Under Review, and the guarantor queue team can log that without being able to decide status. The person who did first pass work cannot remove the Xpert. Moving out of Under Review or Suspended returns them to the level they held before.
- Active and Inactive is voluntary in both directions.

**Screening.** Guarantor queue with a countdown, evidence review with the checklist beside the evidence (pass or fail only, an automatic fail list kept apart, a pass blocked until every item is ticked), reference calls with the script beside the outcome form, and an approvals queue. Every queue item has an owner (take it, hand it back) and a waiting time.

**Settings.** Undecided rules live in a configuration table and are edited from Settings with a reason, each marked Pending until someone saves it. Real checklists and the real call script are set there too.

**Also.** Dashboard queue counts. Xpert pipeline with search and status filter. Xpert record with guarantor, evidence, references, history and placeholders for later phases. A background sweep (hourly, or run by hand) for the deadline, for starting the guarantor clock, and for catching up promotions.

**Admin side.** `docs/SETUP.md`, `scripts/verify-setup.mjs`, `docs/BACKEND_CHANGES.md`.

## Skipped on purpose

- **Revoke access as its own button.** Revoking is a status move (Under Review, Suspended, Removed), so it goes through the same rules, reasons and history instead of a second path.
- **Failed evidence has no exit.** The brief does not say what happens to an applicant whose only evidence fails. They stay in Skill Verification and staff can add new evidence. Decision needed.
- **Clean job promotion.** The rule is built and tested, but there are no jobs in the console yet. It starts working in Phase 4.
- **Notifications to the guarantor.** Staff mark the explainer as sent after sending it themselves. Sending it from the console needs the SMS provider connection and is a later choice.
- **Coordinator table.** Phase 5, where coordinators first matter.

## Assumed (please confirm)

- The Xpert table, its id type and column names. These are settings, not code: `XPERT_TABLE` and the other `XPERT_*` variables. Nothing guesses the table name.
- New applicants' guarantor details sit on the Xpert record today. If they sit elsewhere, the sweep's copy step needs adjusting.
- Backfill rule for existing Xperts: Fully Active with at least one completed job, otherwise Provisionally Active, verification source set to BeyondX directly. Clean feedback cannot be checked until Phase 5, so this uses completed jobs only. The list is shown first.
- Working values for pending rules: 3 unanswered calls make a reference unreachable, 1 clean job lifts to Fully Active, no reverification gap, Under Review keeps access.
- Starter checklist and starter call script are generic placeholders, labelled as such on screen, until real ones are saved in Settings.
